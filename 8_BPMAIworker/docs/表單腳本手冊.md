# 表單腳本（.js）撰寫手冊

> 依據：`samples/太陽能ECRECN/表單/SolarEnergyECRECN.js`（上線中，14 KB）的實際寫法，
> 加上 [BPM5892/BPM_表單腳本可用資源.md](../../BPM5892/BPM_表單腳本可用資源.md) 的資源清冊。
> **撰寫任何表單 JS 之前先讀那份清冊**（AGENTS.md 7.6 已列為必查）。

腳本存在 `.form` 的 `<script>` 標籤裡，內容是逃脫過的 JavaScript。
`1_xml_tool` 已有「萃取成 `.js` → 編輯 → 逃脫回寫」的雙向功能，**沿用它，不要另寫**。

## 1. 生命週期函式（骨架，一律產生）

```javascript
function formCreate()   { return true; }   // 表單建立
function formOpen()     { return true; }   // 每次開啟（含每個關卡）
function formSave()     { return true; }   // 存檔前；return false 可擋下存檔
function formClose()    { return true; }   // 關閉
function formDispatch() { return true; }   // 送出／派送
```

- **`formSave` 的回傳值是必填檢核的落點**。ECRECN 的作法是 `return nullAlert();`，
  `nullAlert()` 蒐集空值欄位、`alert` 後回傳 `false` 擋下存檔。
- `formOpen` 是初始化的落點：顯示／隱藏欄位、抓當前使用者、設定預設值。

## 2. 執行期就有的全域變數（不用宣告）

實測 ECRECN 直接使用、無任何宣告或取值程序：

| 變數 | 內容 |
|:---|:---|
| `activityId` | **當前關卡 ID** —— 分關卡行為全靠它 |
| `processId` | 流程 ID |
| `processInstOID` | 流程實例 OID |
| `formInstOID` | 表單實例 OID |
| `userId` / `userName` | 當前使用者帳號／姓名 |
| `workItemSource` | 待辦來源（ECRECN 用 `== "0"` 判斷是否為正常簽核） |

**分關卡行為的標準寫法**：

```javascript
const setApprovalValue = {
  ERBS2100UserTask: "ERBS2100ApprovalRecordTextBox",
  ERBS3100UserTask: "ERBS3100ApprovalRecordTextBox",
};
if (activityId in setApprovalValue) {
  FormUtil.setValue(setApprovalValue[activityId], [newValue]);
}
```

用查表而不是 `if/else` 串接——AI 產生時一律採這個形式，關卡多了才不會失控。

## 3. FormUtil（頁面已預載，直接用）

ECRECN 實際用到的方法（**這不是完整 API 清單，只是實測用過的**）：

| 方法 | 用法 |
|:---|:---|
| `FormUtil.getValue(id)` | **回傳陣列**，取單值要 `[0]` |
| `FormUtil.setValue(id, [值])` | **第二參數是陣列** |
| `FormUtil.show(["id1","id2"])` / `FormUtil.hide([...])` | 顯示／隱藏，吃陣列 |
| `FormUtil.setOption(id, ...)` | 設定下拉選項 |
| `FormUtil.transToDialog({gridId, inputId})` | 把分頁元件轉成抽屜式對話框 |
| `FormUtil.showGridDialog(...)` / `hideGridDialog(...)` | 開關表格對話框 |

**取值一定要記得 `[0]`**：

```javascript
let sn = FormUtil.getValue("SerialNumber")[0];   // ✅
let sn = FormUtil.getValue("SerialNumber");      // ❌ 拿到的是陣列
```

## 4. 事件函式的命名慣例

元件事件對應的函式名是 `{元件ID}_{事件名}`：

```javascript
function ChgItemDropDown_onchange() { ... }
function ExtraDataAddButton_onclick() { ... }
```

表格元件另有 `${GridId}_add_onclick` 與物件變數 `${GridId}Obj`——
`1_xml_tool/core/form_handler.py` 改元件 ID 時會一併更新這兩者。
**AI 產生的事件函式必須遵守這個命名**，否則改 ID 時會漏改。

## 5. 要載什麼、不要載什麼

### 已預載，直接用（載了反而會版本衝突）

jQuery 3.x、DWR `engine.js`/`util.js`、`FormUtil`、`OpenWin`、`ModalDialog`、
`Dialog`、`ds.js`、`formValidation`、`BpmTable`、`BpmCalendar`、Bootstrap、
`knockout`、`jquery.qrcode`、`jSignature`。

> `CustomJsLib` 裡的 `jQuery-1.7.2.js` 是舊版，與預載的 3.x **混用會出問題**。

### 常用的三個外掛（ECRECN 的寫法）

```javascript
document.write('<script src="../../CustomJsLib/EFGPShareMethod.js"></script>');            // 開窗、下拉、欄位控制 21 函式
document.write('<script src="../../dwrDefault/interface/ajax_DatabaseAccessor.js"></script>'); // 查資料庫
document.write('<script src="../../js/CustomDataChooser.js"></script>');                   // 資料選擇器
```

路徑一律 `../../`，因為腳本的執行位置是 `/NaNaWeb/某模組/某頁面`。

`dwrDefault/interface/` 底下**沒有實體檔案**，是 DWR 依 `dwr-default.xml` 執行期動態產生的，
在檔案總管找不到但 URL 載得到。

### DWR 服務清單

45 支 / 866 個方法，完整清單見資源手冊。AI 產生腳本時常用的：

| 服務 | 用途 |
|:---|:---|
| `ajax_DatabaseAccessor` | 查資料庫（35 個方法） |
| `ajax_OrgAccessor` | 查人／查組織／算工作天（`findCurrentUser`、`countWorkingTime`） |
| `ajax_FormAccessor` | 查表單實例與欄位值 |
| `ajax_ProcessAccessor` | 流程操作、動態加簽會辦 |

用法：

```javascript
ajax_DatabaseAccessor.executeQuery(dbId, sql, params, types, function (result) { ... });
```

## 6. 自訂檔案上傳（iframe 掛載）

不走 BPM 內建附件、改掛自家上傳服務時的寫法。
表單那一側要準備什麼見 [表單生成手冊.md](表單生成手冊.md) 第 9 節。

### 6.1 現行寫法（線上表單 SolarEnergyECRECN）

```javascript
function ViewChangeIframe(changeHtmlId, filter) {
  const url = uploadURL("view", filter);
  const originalElement = document.getElementById(changeHtmlId);
  if (originalElement) {
    const iframe = document.createElement("iframe");
    iframe.id = changeHtmlId;                   // 沿用原元件的 id
    iframe.src = url;
    originalElement.parentNode.replaceChild(iframe, originalElement);   // 取代元件
    iFrameResize({ ... }, `#${changeHtmlId}`);
  }
}
```

搭配一支組 URL 的函式：

```javascript
// FileUpload/:sourceApplication/:sourceNumber/:userNumber/:platform/:role/:class/:filter
function uploadURL(roleValue, filterValue) {
  const host = "http://<上傳服務主機>/GigaSolarBPM/FileUpload/";
  const sourceNumber = FormUtil.getValue("BPMBackFormIdHidden")[0];   // 自家單號
  return `${host}${系統名}/${sourceNumber}/${userId}/BPM/${roleValue}/${類別.join("|")}/${filterValue}`;
}
```

`role` 用 `edit` / `view` 區分能不能上傳 —— **這是唯一能控制 iframe 內權限的地方**，
鼎新的欄位權限管不到 iframe 裡面。

### 6.2 現行寫法的三個實際問題

都是從線上這支表單讀出來的，不是假設：

| 問題 | 依據 | 後果 |
|:---|:---|:---|
| **iframe 沿用原元件的 id** | `iframe.id = changeHtmlId` | 之後 `FormUtil.getValue(該 id)` 與 `document.getElementById(該 id)` 拿到的是 iframe，不是欄位 |
| **`replaceChild` 把元件移出 DOM** | 同上 | 存檔時那一格收不到值，**而且不會報錯**。這支表單沒出事，是因為被換掉的兩個 TEXTAREA（`ECContentDescAttTextArea`、`ECSpecAttTextArea`）實測在 25 個關卡的 `formFieldAccessControl` 裡**一次都沒出現過**，本來就不可編輯 —— 這是巧合，不是保障 |
| **同一個掛載點被掛兩次** | `ViewChangeIframe` 在 `openSet()` 呼叫 2 次，又在 `openSetValue()` 的 axios callback 裡再呼叫 2 次 | 第二次 `getElementById` 找到的是第一次做出來的 iframe，於是「用新 iframe 取代舊 iframe」，白做一次、載入兩次 |

### 6.3 建議寫法 —— 掛載點看、按鈕傳

定案的作法拆成兩半，**權限交給流程，不要寫在腳本裡**：

| 動作 | 誰做 | 模式 | 誰控制 |
|:---|:---|:---|:---|
| **看已上傳的檔案** | `formOpen()` 掛一個 iframe | 固定 `view` | 不必控制，每個關卡都看得到 |
| **上傳檔案** | 一顆按鈕開新視窗 | 固定 `edit` | **流程的按鈕權限**（`formFieldAccessControl`） |

掛載點用 `LABEL` 或 `IMAGE` 這種不存值的元件（見 [表單生成手冊.md](表單生成手冊.md) 第 9 節），
iframe 用 `insertBefore` 插在它後面，**不取代任何元件**。

```javascript
// ── 掛載：formOpen 時只掛「查看模式」的 iframe ───────────────
function mountUploadFrame(anchorId, filter, minHeight) {
  const frameId = anchorId + "_uploadFrame";
  if (document.getElementById(frameId)) {
    return;                                  // 已掛載，直接返回（避免重複掛）
  }

  const anchor = document.getElementById(anchorId);
  if (!anchor) {
    console.error("找不到上傳區掛載點：" + anchorId);
    alert("上傳區載入失敗，請通知系統管理員。");
    return;
  }

  const iframe = document.createElement("iframe");
  iframe.id = frameId;                       // ★ 不要沿用 anchorId
  iframe.src = uploadURL("view", filter);    // ★ 固定 view，開啟時一律是查看模式
  iframe.style.width = "100%";
  iframe.style.height = (minHeight || 800) + "px";
  iframe.style.border = "1px solid #ccc";
  iframe.frameBorder = "0";
  iframe.scrolling = "yes";

  anchor.parentNode.insertBefore(iframe, anchor.nextSibling);

  iFrameResize({ checkOrigin: false, heightCalculationMethod: "max" }, "#" + frameId);
}

// ── 上傳：獨立一顆按鈕，開 edit 模式的視窗 ────────────────────
function AttUploadButton_onclick() {
  const win = window.open(uploadURL("edit", "查詢全部"), "_blank",
                          "toolbar=no,location=no");
  if (!win) {
    alert("瀏覽器擋掉了上傳視窗，請允許此站台開啟彈出視窗。");
    return;
  }
  // 上傳視窗關掉後把查看用的 iframe 重載一次，新上傳的檔案才會出現
  const timer = setInterval(function () {
    if (win.closed) {
      clearInterval(timer);
      reloadUploadFrame("UploadAreaLabel");
    }
  }, 800);
}

function reloadUploadFrame(anchorId) {
  const f = document.getElementById(anchorId + "_uploadFrame");
  if (f) {
    f.src = f.src;                           // 重載，讓新檔案顯示出來
  }
}

// ── formOpen 裡呼叫 ─────────────────────────────────────────
function formOpen() {
  mountUploadFrame("UploadAreaLabel", "查詢全部", 800);
  return true;
}
```

### 6.3.1 ★ 不要用 `activityId` 決定能不能上傳

```javascript
// ❌ 不要這樣寫
iframe.src = uploadURL(activityId === "ApplyUserTask" ? "edit" : "view", filter);
```

理由：

- **權限會散在兩個地方**（流程定義的按鈕權限 + 腳本裡的關卡清單），改流程時腳本一定會忘了跟著改。
- 加關卡、加簽、會辦、跳關的時候，腳本裡那份關卡清單必漏。
- 流程的按鈕權限本來就是為這件事設計的：**按鈕沒被列進該關卡的 `formFieldAccessControl` 就是唯讀**，
  使用者按不到，腳本自然不會被呼叫。

所以腳本只管「怎麼做」，「誰可以做」一律交給流程設計。

### 6.3.2 重點差異對照

| | 現行 `ViewChangeIframe` | 建議寫法 |
|:---|:---|:---|
| 掛法 | `replaceChild` 取代元件 | `insertBefore` 插在掛載點後面 |
| 掛載點 | 有值的 `TEXTAREA` | 不存值的 `LABEL` / `IMAGE` |
| iframe id | 沿用元件 id | `{掛載點}_uploadFrame` |
| 重複掛載 | 會（實測掛 2 次） | 用 frameId 當旗標擋掉 |
| 上傳權限 | iframe 的 `role` 參數 | **流程的按鈕權限** |
| 上傳後更新 | 無 | 視窗關閉後重載 iframe |

### 6.4 一定要記得的兩件事

1. **上傳按鈕一定要列進流程的欄位權限。** 掛載點（LABEL）不必列，
   但**按鈕沒列進任何一個關卡的 `formFieldAccessControl`，就等於全流程都不能上傳**。
   按鈕 ID 也一定要以 `Button` 結尾，否則 `bpmn_handler` 會把它歸類成欄位而不是按鈕。
2. **上傳服務的單號要自己給。** 線上是另外開一個隱藏欄
   （`BPMBackFormIdHidden`）在 `formOpen()` 時產生一組唯一值存起來，
   之後所有上傳／查詢都用它當 `sourceNumber`。
   **不要拿 BPM 的 `SerialNumber` 當 key** —— 它在流程送出前可能還是空的。
3. **外部上傳的檔案，`7_proc_export` 的稽核匯出查不到。**
   需要進稽核軌跡的檔案還是要走 BPM 內建的 `Attachment` 元件。

## 7. 禁忌

| 禁忌 | 理由 |
|:---|:---|
| **引用外部／非 BPM 主機的 CDN** | ECRECN 現有腳本指向 `http://10.10.130.122:5148/...`（axios、iframe-resizer）與 `:5123` 的 nanoid API。那台不是 BPM 主機，停機或改 IP 會讓所有引用它的表單一起壞。AI 產生的新腳本**不要再增加這類相依**；需要的套件放進 `NaNaWeb/CustomJsLib/`。 |
| **`ajax_DatabaseAccessor.executeUpdate` 等寫入方法** | DWR 沒有方法白名單，瀏覽器端可直送 SQL 寫入。除非明確被要求，AI 一律只產生查詢，不產生寫入。 |
| **重複載入已預載的函式庫** | 版本衝突 |
| **`try { } catch(e) { }` 吞錯誤** | AGENTS.md 第 6 節：失敗要明確說。腳本錯誤要 `console.error` 或 `alert`。 |
| **在腳本裡寫死帳密或連線字串** | AGENTS.md 第 8 節 |
| **`replaceChild` 把有值的欄位換成 iframe** | 元件被移出 DOM，存檔時那一格收不到值，而且不報錯（見第 6 節） |

## 8. AI 該產生到什麼程度

`script_builder` 產生的是**骨架與空殼，不是完整業務邏輯**：

會產生：
- 五個生命週期函式
- IR 的 `script.events` 列出的每個事件函式（空殼，含中文註解說明該做什麼）
- IR 的 `script.libs` 對應的 `document.write` 載入列
- 必填檢核 `nullAlert()`（依 IR 中 `required: true` 的欄位自動生成）
- 分關卡行為的查表骨架（依 `process_ir` 的關卡清單）

不會產生：
- 具體的 SQL
- 對接 ERP 的邏輯
- 任何需要業務知識才寫得出來的計算

**產生不出來的地方要留 `// TODO:` 並在回報中列出**，不要編一段看起來對的程式碼填空
（AGENTS.md 第 6 節）。
