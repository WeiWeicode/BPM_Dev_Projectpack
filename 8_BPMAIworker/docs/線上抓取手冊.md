# 線上抓取手冊 —— 把既有流程與表單抓下來當範本

⑧ 原本只做「從零生成」。但實務上更常見的需求是
**「照著線上那支流程做一支類似的」** —— 這份手冊講的是前半段：
把線上既有的流程、表單、表單 JavaScript 一次抓齊。

工具：[`tools/fetch_online.py`](../tools/fetch_online.py)

---

## 1. 提示詞（給 AI agent 用）

要 agent 做這件事時，照下面這樣講就夠了：

```
使用 AIworker，去線上正式區抓 MIS問題反應單 SIC005 的流程跟表單，
用 08 的 tool 抓欄位、JavaScript、關卡。
```

agent 收到這種指令時要做的事，固定是這四步：

| 步 | 動作 | 指令 |
|:---|:---|:---|
| 1 | 確認流程 ID 存在、有沒有同名前綴的別支流程 | `fetch_online.py --list --keyword <關鍵字> --host <190\|191>` |
| 2 | 抓取 | `fetch_online.py --process <流程ID> --host <190\|191>` |
| 3 | 讀 `out/<host>_<流程ID>_v<n>/摘要.md`，先看兩個 ⚠️ 區塊 | — |
| 4 | 要改腳本時，讀 `腳本/<表單ID>_v<n>.腳本盤點.md` 當工單 | — |

**講「正式區」就是 `--host 190`，講「測試區」就是 `--host 191`。**
沒講就問，不要猜 —— 兩區的同名流程版本常常不一樣。

### 這個提示詞背後的邊界

- 本工具**只做 SELECT**，經 `bpm_kb.db.Database(readonly=True)`、一律參數化。
- **不呼叫 SOAP**。AGENTS.md 8.1 對 190 的 API 禁令不變 ——
  開單、簽核、作廢一律只在 191 測試區走 ⑤ `5_ws_explorer`。
- 產出寫到 `8_BPMAIworker/out/`，該目錄已列入 `.gitignore`。
  **裡面是正式區的實際表單內容與員工欄位，不要複製到 `samples/` 或任何進版控的位置。**

## 2. 指令

```bash
python 8_BPMAIworker/tools/fetch_online.py --list --keyword MIS --host 190
```

```bash
python 8_BPMAIworker/tools/fetch_online.py --process SIC005 --host 190
```

| 參數 | 說明 |
|:---|:---|
| `--host` | `191`（預設，測試區）／`190`（正式區，只 SELECT） |
| `--process` | 流程 ID，**精確比對** |
| `--form` | 額外要抓的表單 ID，可重複；關卡權限沒落地時用得到 |
| `--version` | 流程版本，預設取已發佈（`RELEASED`）的最大版 |
| `--list` | 只列出符合 `--keyword` 的流程與表單，不抓 |
| `--out` | 輸出根目錄，預設 `8_BPMAIworker/out` |

### 為什麼 `--process` 是精確比對

線上真的有這種資料：

| ID | 名稱 |
|:---|:---|
| `SIC005` | MIS問題反應單 |
| `SIC005_` | ERP開帳申請單 |

`LIKE '%SIC005%'` 會把兩支都撈出來，而且 `SIC005_` 有 20 個版本、
`SIC005` 只有 2 個，按版本排序會讓錯的那支排在最前面。
所以 `--list` 用模糊比對找、`--process` 用精確比對抓。

## 3. 產出

```text
8_BPMAIworker/out/<host>_<流程ID>_v<n>/
├── 摘要.md                          ★ 先看這份
├── 流程/
│   ├── <流程ID>_v<n>.bpmn           ProcessDefinition.bpmXML 原文
│   └── 流程結構.json                 關卡、連線、執行者、欄位權限（含 orphaned 標記）
├── 表單/
│   ├── <表單ID>_v<n>.form           FormDefinition.defSerialize 原文
│   ├── <表單ID>_v<n>.欄位.json       用 1_xml_tool/core 反解出來的欄位清單
│   └── <表單ID>_v<n>.rwdLayout.json  只有響應式表單才會有
└── 腳本/
    ├── <表單ID>_v<n>.js              FormDefinition.script
    ├── <表單ID>_v<n>.mobile.js       FormDefinition.mobileScript
    └── <表單ID>_v<n>.腳本盤點.md      舊寫法盤點
```

### 抓下來的 `.bpmn` 不等於設計師匯出的 `.bpmn`

`ProcessDefinition.bpmXML` **只有畫布座標**，流程邏輯散在
`ActivityDefinition` / `TransitionDefinition` / `ParticipantDefinition`
等關聯表裡（AGENTS.md 7.1）。所以：

- 邏輯要看 `流程結構.json`，不是那份 `.bpmn`。
- 那份 `.bpmn` **不能直接匯回設計師**。要可匯入的檔案得從設計師匯出。

`.form` 則相反 —— `defSerialize` 就是整份表單 XML，內容與匯出檔一致。

## 4. 版面：絕對位置 vs 響應式

判定方式只有一條：**`FormDefinition.rwdLayout` 有沒有值。**

| `rwdLayout` | 版面模式 | 座標存在哪 |
|:---|:---|:---|
| 空 | **絕對位置**（舊式） | 各元件的 `elementStyles`（`coordinateX` / `coordinateY`） |
| 有值（逃脫過的 JSON） | **響應式**（12 欄格線） | `rwdLayout` 的 `row` / `column` / `elements` |

摘要表的「版面」欄直接寫著是哪一種。

**這件事會決定後續怎麼仿造**：絕對位置的表單，元件位置靠座標；
要照抄版面就得連 `elementStyles` 一起帶，`8_BPMAIworker/templates/` 的空白範本
是絕對位置基底，兩者相容。響應式表單則要另外處理 `rwdLayout` 的格線 JSON。

## 5. 摘要裡的兩個 ⚠️ 區塊

這兩個是**真實問題**，不是工具的解析失敗，不可略過（AGENTS.md 第 6 節）：

| 區塊 | 意思 | 怎麼處理 |
|:---|:---|:---|
| **查不到定義的表單參照** | 關卡權限或主旨範本指到某個表單 ID，`FormDefinition` 裡卻沒有 | 多半是複製流程時把別支流程的關卡權限一起帶過來。仿造時**不要照抄那一關的權限** |
| **對不到表單元件的權限欄位** | 表單有，但那個欄位 ID 在表單最新已發佈版裡不存在 | 流程版本與表單版本脫節。照抄會產生一堆設了權限卻不存在的欄位 |

工具**不會自行挑一個當答案**，兩邊都是合法設定，一律標出來給人工確認。

## 6. 腳本盤點怎麼用

`腳本盤點.md` 是給人決定「要不要改」的清單，不是自動修正。它報三件事：

1. **五個生命週期函式在不在**（`formCreate` / `formOpen` / `formSave` /
   `formClose` / `formDispatch`，見 [表單腳本手冊.md](表單腳本手冊.md)）
2. **自訂函式清單** —— 通常是 `<欄位ID>_onclick` / `<欄位ID>_onchange`，
   函式名就是元件 ID，改欄位 ID 一定要連腳本一起改（① `1_xml_tool` 的 `write_back` 有處理）
3. **舊寫法命中處與行號** —— `document.write`、硬編 IP、串接 SQL、
   `eval`、`alert`、IE 專屬 API 等

盤點規則寫在 `fetch_online.py` 的 `SCRIPT_RULES`，只列「看到就一定是問題」的。
**沒命中不代表沒問題，只代表規則沒涵蓋到** —— 盤點表自己會這樣寫。

## 6.4 抓下來之後要做成新專案：用空白範本重建（**多數情況走這條**）

線上的舊表單是**絕對位置**版面。把 `defSerialize` 改個代號直接匯入，
拿到的還是絕對位置的舊式表單 —— 這幾乎不會是你要的。

要響應式表單，只能以響應式骨架重新長一次：

```bash
python 8_BPMAIworker/tools/build_from_online.py --source out/190_SIC005_v2 --form-id 新表單代號 --process-id 新流程代號 --name 中文名 --out out/新專案
```

| 來源 | 提供什麼 |
|:---|:---|
| `templates/原始空白專案/` | 表單與流程的外殼（`appDesignType=-1`、`rwdLayout=[]`） |
| `samples/快速開發測試/…quickDevTestForm.form` | 27 種元件型別的 XML 片段（響應式、已知可匯入） |
| `fetch_online.py` 的產出 | 欄位 ID／中文名／型別／選項／座標，與整份 JavaScript |

**只有內容來自線上，XML 結構一律沿用兩份已知可匯入的檔案**，不憑空生成標籤。

### 版面怎麼還原

原檔的絕對座標拿來分列：`top` 差距 18px 內視為同一列，列內依 `left` 排序，
12 欄格線一列最多 4 格。這樣重建出來的分組與原本的視覺一致，
而不是把幾十個欄位排成一長條。隱藏欄位不佔版面，收在最後幾列。

**像素級的微調還原不了** —— 格線只能均分欄寬，要細調得進設計器拉。

### 一定要核對選項順序

單選／複選的選項順序決定執行期的 `<欄位ID>_0`、`_1`… DOM id，
腳本直接靠它定位。工具會原封不動搬過去，但匯入後請自己再看一眼。

### 產出後的自動驗證（L1）

工具會反解產出的 `.form` 與來源逐項對比：欄位數、型別、中文名、選項、
腳本是否一字不差、腳本引用的元件 ID 是否都存在、XStream id 是否連號。
**L1 過不代表匯得進去** —— L2、L3 仍然只能人工。

## 6.5 只想換代號、不重建版面：改代號

測試區通常已經有同代號的流程與表單，直接匯入會跳「要不要覆蓋」。
把代號改掉就能與既有版本並存，測完再決定要不要真的蓋上去。

```bash
python 8_BPMAIworker/tools/rename_ids.py --form <抓下來的.form> --form-id 舊=新 --out <輸出目錄>
```

代號會出現在好幾個地方，少改一處就靜默壞掉，所以一律讓工具一次改完：

| 檔案 | 位置 |
|:---|:---|
| `.form` | `<id>`、`<script>` 內的 `DataSource("表單ID", "SQL名")` |
| `.bpmn` | `<id>` / `<mainProcessDefinitionId>`、`<formDefinitionId>`、`<formFieldAccessControl>` 內二次逃脫的 `&lt;表單ID&gt;`、`<subjectTemplet>` 內的 `&lt;#表單ID~~欄位&gt;` |

改完會一併重配 OID（做法與 `new_project.py` 相同），避免與線上既有定義撞號。

### 兩個一定要知道的限制

**一、`fetch_online.py` 抓下來的 `.bpmn` 不能拿去改名匯入。**
它的根標籤是 `<Diagram>`，只有畫布座標；設計器要的是
`<com.dsc.nana.domain.workflow__definition.ProcessPackage>`（見第 3 節）。
`rename_ids.py` 會直接擋下來並說明原因。**流程要改代號匯入，只能請設計器先匯出一份。**

**二、流程變數（`relevantDataDefinition`）習慣與表單同名，但工具不會自動改。**
流程靠 `<formDefinitionId>` 綁表單，變數叫什麼都能跑；
但 16 處 `relevantDataDefinitionId` 要改就得一起改。
兩種做法都合法，所以工具只把殘留處報出來，不自行決定。

### 資料庫的 `.form` 與設計器匯出的 `.form` 不是同一種序列化

實測 `MIS_Application` v2：

| | XStream `id=` 屬性 | `reference=` 屬性 | `appDesignType.value` |
|:---|---:|---:|:---|
| 資料庫 `defSerialize` | 0 個 | 617 個（**XPATH 相對路徑**） | `3` |
| 設計器匯出（太陽能ECRECN） | 2334 個 | 139 個（數字） | `-1` |

兩種都是合法的 XStream 序列化，讀取端會自行判斷，但**「資料庫的 `.form` 匯得進設計器」
這件事目前沒有實測過**（PLAN.md 第 7 節的未知數 4）。第一次匯入請在測試區做。

## 7. 已知限制

- **只抓得到定義層**，抓不到實例（誰在哪一關卡了幾天）。那是 ⑥ `6_todo_viewer` 的事。
- **抓不到流程層的腳本**：`ServiceTask` 的 Call Out 設定、`DecisionRuleTask` 的規則式
  存在別的關聯表，目前沒抓。要看的話走 ③ `3_db_explorer` 手動查。
- **不處理多版本比對**。要看某支流程改了什麼，得抓兩次不同 `--version` 再自己 diff。
- **抓下來的 `.bpmn` 無法匯入**，見 6.5。這是資料模型的限制，不是工具沒做。
- `--list` 的關鍵字同時比對 ID 與中文名，資料量大時會慢（沒有索引可用）。
