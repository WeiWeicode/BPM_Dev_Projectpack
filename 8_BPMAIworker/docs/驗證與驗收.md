# 驗證與驗收

> 生成類工具最大的風險不是「做不出來」，是「做出一個看起來對、匯入才炸的檔案」。
> 本文定義五層驗證，**每一層都要能明確回答通過或沒通過，不接受「應該可以」**。

---

## 1. 五層驗證

| 層 | 名稱 | 自動化 | 檢查什麼 |
|:--:|:---|:---:|:---|
| V1 | IR 校驗 | ✅ | IR 本身自洽 |
| V2 | 靜態 lint | ✅ | 產出物的內部一致性 |
| V3 | 往返還原 | ✅ | 樣板與編號規則是否吃透 |
| V4 | 反解對比 | ✅ | 產出物反解回來等不等於 IR |
| V5 | 匯入與實跑 | ❌ 人工 | 鼎新設計師收不收、單走不走得完 |

V1～V4 是程式該保證的（對應 PLAN.md 的 L1）；V5 目前**沒有任何自動化手段**。

---

## 2. V1 —— IR 校驗

| 檢查 | 失敗訊息要說什麼 |
|:---|:---|
| 所有 ID 符合 `^[A-Za-z_][A-Za-z0-9_]*$` | 哪個 ID、違反哪一條 |
| 表單內欄位 ID 唯一；流程內關卡 ID 唯一 | 重複的是哪幾個 |
| 按鈕型別的 ID 以 `Button` / `Btn` 結尾 | 哪個按鈕沒有後綴、會被歸類成欄位 |
| `SELECT`／`RADIO`／`CHECKBOX`／`DROPDOWN` 有 `options` | 哪個欄位缺選項 |
| `LIST` 有 `columns`，且每欄有 `caption` | 哪個表格缺欄位標題 |
| `layout` 同列 `span` 總和 ≤ 12 | 第幾列超出多少 |
| 權限值只能是 `ENABLED` / `INVISIBLE` / `FULL_CONTROL` | 出現了什麼非法值 |
| **`permissions` 的每個 key 存在於 `form_ir.fields`** | 哪個關卡引用了不存在的欄位 |
| `process_ir.formId` == `form_ir.formId` | 兩邊各是什麼 |
| `transitions` 兩端的關卡都存在 | 哪條連線指向不存在的關卡 |
| 恰好一個 `StartEvent`、至少一個 `EndEvent` | 目前有幾個 |
| 從 `StartEvent` 可達所有關卡 | 哪幾關孤立 |

倒數第五項是最重要的一條：`5_ws_explorer` 的手冊記載
「`invokeProcess` 不驗證表單欄位 id，錯的欄位靜默寫入、之後讀取才炸」。
權限字串的欄位 ID 打錯是同一類地雷——**不會報錯，只是那個欄位永遠打不開**。

## 3. V2 —— 靜態 lint（對產出物）

### `.form`

- [ ] XStream `id` 屬性為 1…N **嚴格連號、無重複**
- [ ] 每個 `reference="M"` 的 M 都存在於 id 集合中
- [ ] `rwdLayout` 內的元件 ID 集合 == `elementDefinitions` 內的元件 ID 集合
- [ ] 每個非空 `label` 的欄位都有配對的 Label（`lbl_` 前綴或 `pairId`）
- [ ] `<script>` 反逃脫後是合法的 JavaScript（至少括號配對、能被 `node --check` 收下）
- [ ] 檔案為 UTF-8；BOM 的有無與來源樣板一致

### `.bpmn`

- [ ] 所有 `<OID>` 互異
- [ ] `bpmXML` 的 `Node Id` 集合 == `activityDefinitions` 的 ID 集合
- [ ] `bpmXML` 的 `DiagramLink` 數 == `transitionDefinitions` 數
- [ ] 每個 `formFieldAccessControl` 反逃脫後是合法 XML，且第一層標籤 == `formDefinitionId`
- [ ] `workflow__definition`（雙底線）只出現在標籤名；
      `class=` 與 `reference=` 一律 `workflow_definition`（單底線）
- [ ] `objectVersion` 全為 `1`

## 4. V3 —— 往返還原（M1 的驗收判準）

**這是整個專案最關鍵的一項測試。**

```
既有 sample（.form / .bpmn）
   → 反推成 IR
   → 用 builder 重新組裝
   → 與原檔逐位元組比對
```

位元組完全相同才算通過。過不了代表樣板切得不對、或編號／OID 規則沒吃透，
**這時候繼續往下做 M2、M3 都是浪費**。

可用的兩個基準檔：
- `samples/快速開發測試/表單/原檔案-quickDevTestForm.form`（27 種元件，型別覆蓋最全）
- `samples/快速開發測試/流程/已完成匯入_測試快速開發-欄位權限.bpmn`（含實際權限設定）

> 這個判準的精神跟 `2_web_builder/test_core.mjs` 的「回寫位元組不變」測試一致
> （AGENTS.md 7.2 稱之為硬性門檻）。差別是那邊測「改一格後其餘不變」，
> 這邊測「整份重建後完全相同」，更嚴格。

## 5. V4 —— 反解對比

用**既有的**解析器把產出物讀回來，跟 IR 比：

```python
from core import form_handler, bpmn_handler
extracted = form_handler.extract(out_form_path)
# 逐欄位比對 id / name(label) / type 與 form_ir
```

必須用 `1_xml_tool/core`，不能用 builder 自己的內部結構——
自己驗自己等於沒驗。

比對項目：

| 產出 | 比對什麼 |
|:---|:---|
| `.form` | 每個欄位的 `id`、`name`（中文標籤）、`type` |
| `.bpmn` | 每個關卡的 `id`、`name`、`type`；每關的 `buttons` 與 `fieldPermissions` 清單與權限值；`formId` |

交叉基準：同一份 `.bpmn` 用 `2_web_builder` 的 JS 核心解析，
結果應與 Python 端一致（`node test_core.mjs` 的交叉驗證精神）。

## 6. V5 —— 匯入與實跑（人工）

**目前沒有自動化的辦法，也不要假裝有。**

| 步驟 | 環境 | 通過標準 |
|:---|:---|:---|
| 匯入表單 | 191 測試區設計師 | 能開啟、版面不跑位、無 `Cannot read properties of null` |
| 匯入流程 | 同上 | 流程圖完整、關卡連線正確 |
| 檢查權限 | 用 `2_web_builder` 載入產出的 `.bpmn` | 權限矩陣與 IR 一致 |
| 發佈後開單 | `5_ws_explorer` 對 **191 測試區** | 各關卡欄位可編輯／唯讀／隱藏符合 IR |
| 走完流程 | 同上 | 每關 `acceptWorkItem` → `completeWorkItem` 都成功 |

邊界（AGENTS.md 8.1）：
- **190 正式區一律不連**，連唯讀查詢都不行。
- 測試區產生的新單可以留著，但**不可刪除既有資料**。
- 呼叫 API 前記得：使用者 OID 取 `Users.OID` 不是 `Employee.OID`；
  `completeWorkItem` 之前一定要先 `acceptWorkItem`。

## 7. 回報格式

每次產生完，回報必須包含：

```
產出檔案：
  out/SolarEnergyECRECN.form        （124 個元件、含 62 個 Label）
  out/SolarEnergyECRECN.js          （5 個生命週期函式、3 個事件空殼、2 處 TODO）
  out/太陽能ECRECN確認單.bpmn        （25 關卡、28 連線、9 關設有欄位權限）

驗證結果：
  V1 IR 校驗      通過
  V2 靜態 lint    通過
  V3 往返還原     不適用（新檔案，無原檔可比）
  V4 反解對比     通過（124/124 欄位、25/25 關卡、152/152 權限項）
  V5 匯入實測     ✗ 尚未執行，需人工匯入 191 測試區

尚未完成：
  - ExtraDataAddButton_onclick 的資料查詢 SQL（TODO，需業務規則）
  - ParticipantDefinition 的 type 一律填 PROCESS_REQUESTER，
    ECRECN 原檔另有其他值，尚未盤點
```

**沒跑的就寫沒跑，不要寫「應該可以」。** 產出物本身沒有「部分成功」——
匯不進設計師就是零分，所以 V5 沒做就必須明說（AGENTS.md 第 6 節）。
