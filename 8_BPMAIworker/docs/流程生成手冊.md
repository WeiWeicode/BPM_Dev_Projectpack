# .bpmn 生成手冊

> 依據：`samples/快速開發測試/流程/原檔案-測試快速開發.bpmn`（114 KB、7 關卡、76 個 OID）
> 與 `samples/太陽能ECRECN/流程/太陽能 ECRECN 確認單(碩禾).bpmn`（437 KB、25 關卡、上線中）。
> 解析與驗證一律用 `1_xml_tool/core/bpmn_handler.py`。

---

## 1. 先認清一件事

**資料庫裡沒有 `.bpmn`。** 它是設計師把 `ProcessDefinition` 及其關聯表
（`ActivityDefinition` / `TransitionDefinition` / `ParticipantDefinition` /
`FormFieldAccessDefinition`）重新序列化出來的匯出格式（AGENTS.md 7.1）。

所以本手冊描述的是**匯出檔的格式**，不是資料庫結構。
兩者的對應關係在 [../../README.md](../../README.md) 的「資料模型速查」。

---

## 2. 檔案骨架

```xml
<com.dsc.nana.domain.workflow__definition.ProcessPackage>
  <firstActIsReqstPerform>false</firstActIsReqstPerform>
  <flowType>SignatureFlow</flowType>
  <formInstanceType>0</formInstanceType>
  <header>
    <bpmnVersion>2.0</bpmnVersion>
    <createdTime>2026-08-20 14:26:58.0</createdTime>
    <vendor>Data Systems Consulting</vendor>
    <xpdlVersion>1.0</xpdlVersion>
    ... OID / objectVersion / dto / dtoState ...
  </header>
  <id>quickDevTestProcess</id>
  <isUsedTemplate>false</isUsedTemplate>
  <mainProcessDefinitionId>quickDevTestProcess</mainProcessDefinitionId>
  <name>測試快速開發</name>
  <processDefinitions>
    <com.dsc.nana.domain.workflow__definition.ProcessDefinition>
      <activitySetDefinitions>...</activitySetDefinitions>
      <applicationDefinitions>...</applicationDefinitions>
      <activityDefinitions>      ← 關卡
      <transitionDefinitions>    ← 連線
      <participantDefinitions>   ← 執行者
      <relevantDataDefinitions>  ← ★ 綁哪張表單
      <bpmXML>                   ← 畫布座標（逃脫 XML）
      ...
    </com.dsc.nana.domain.workflow__definition.ProcessDefinition>
  </processDefinitions>
  ...
</com.dsc.nana.domain.workflow__definition.ProcessPackage>
```

注意類別名稱裡的**雙底線** `workflow__definition`：
那是 XStream 對套件名裡底線的逃脫（實際類別是 `workflow_definition`）。
但 `class=` 與 `reference=` 屬性裡用的是**單底線**的真實類別名：

```xml
<container class="com.dsc.nana.domain.workflow_definition.ProcessDefinition" reference="../../.."/>
```

**寫錯任一邊都會解析失敗。** 樣板複製時千萬別「順手修正」。

## 3. ★ OID 配發規則

實測 `原檔案-測試快速開發.bpmn`：

```
76 個 <OID>，全數互異
其中 74 個後綴相同： f9e21004851cac97a977dbbf   （24 碼，機器／連線識別）
前 8 碼遞增：        3ef96b08 / 3ef96b09 / 3ef96b0b / 3ef96b0c …（時間戳）
另 2 個為外來 OID（引用既有定義帶進來的）
```

`.form` 也是同一套：`containerOID` 為 `3c184ddc` + `f9e21004851cac97a977dbbf`。

組裝器的作法：固定一組 24 碼後綴，前 8 碼由計數器遞增配發，全檔唯一。

> ⚠️ **未驗證的關鍵問題**：匯入時鼎新是重新配發 OID，還是沿用檔案內的值？
> 若沿用，自編 OID 與線上既有資料撞號的後果未知。
> 在問到答案之前，M2 的保守作法是**沿用一份既有可匯入檔案的 OID 配發區段**，
> 而非憑空生成新的後綴。

`objectVersion` 一律 `1`（它是 OJB 的樂觀鎖計數器，與業務版本無關，AGENTS.md 7.4）。

## 4. ActivityDefinition —— 關卡

**單一關卡有 67 個直屬子標籤、約 9.8 KB**，其中 IR 只決定 4 格：

| 標籤 | 來源 |
|:---|:---|
| `<id>` | IR `activities[].id` |
| `<name>` | IR `activities[].name` |
| `<bpmnType>` | IR `activities[].type` |
| `<formFieldAccessDefinition>` → `<formFieldAccessControl>` | IR `activities[].permissions` |

其餘 63 格（`ableToAskActivityReexecuteType`、`autoDelivery`、`finishMode`、
`multiNotification`、`straightSignOff`、三段 `Notice` 設定…）**全部照關卡型別的樣板複製**。
這些是設計器上「關卡屬性」那幾十個勾選框的持久化，與 AI 要做的事無關。

### 支援的關卡型別（教材檔實測 7 種）

| `bpmnType` | 用途 | 可設欄位權限 |
|:---|:---|:---:|
| `StartEvent` | 起點 | ✗ |
| `EndEvent` | 終點 | ✗ |
| `UserTask` | 人工簽核關卡 | ✅ |
| `ManualTask` | 人工任務 | ✅ |
| `SendTask` | 系統通知 | ✗ |
| `DecisionRuleTask` | 核決層級 | ✗ |
| `ParallelGateway` | 平行分歧／匯合（ECRECN 有用到） | ✗ |

## 5. TransitionDefinition —— 連線

最簡單的一段，只有三格有意義：

```xml
<com.dsc.nana.domain.workflow__definition.TransitionDefinition>
  <container class="com.dsc.nana.domain.workflow_definition.ProcessDefinition" reference="../../.."/>
  <fromActivityDefinitionId>UserTask_3</fromActivityDefinitionId>
  <id>Link_6</id>
  <name></name>
  <toActivityDefinitionId>UserTask_4</toActivityDefinitionId>
  ... OID / objectVersion / dto / dtoState ...
</com.dsc.nana.domain.workflow__definition.TransitionDefinition>
```

`<id>` 慣例為 `Link_{n}`。連線的 ID 在 `bpmXML` 的 `DiagramLink` 裡會再出現一次。

## 6. ParticipantDefinition —— 執行者

```xml
<containerOID>3ef96b0ef9e21004851cac97a977dbbf</containerOID>
<id>PAR17872072404124</id>
<includeSubUnit>true</includeSubUnit>
<type><value>PROCESS_REQUESTER</value></type>
```

- `<id>` 是 `PAR` + 時間戳數字，自動產生即可。
- `containerOID` 指向所屬的關卡。
- `type` 的值見 [AI產生規格_IR.md](AI產生規格_IR.md) 第 6 節。
  ⚠️ 值域尚未完整盤點，需要時用 `3_db_explorer` 查實際分布，不要自行編造。

## 7. relevantDataDefinitions —— 綁哪張表單

**這是流程與表單在匯出檔裡唯一的正式綁定點**：

```xml
<com.dsc.nana.domain.workflow__definition.RelevantDataDefinition>
  <containerOID>4b8b0290f9e21004851cac97a977dbbf</containerOID>
  <dataType class="com.dsc.nana.domain.workflow_definition.FormType">
    <formDefinitionId>quickDevTestFormImport</formDefinitionId>
    ...
  </dataType>
  <id>quickDevTestFormImport</id>
  <initialValue></initialValue>
  <isArray><value>FALSE</value></isArray>
  <length>0</length>
  <name>快速開發測試</name>
  ...
</com.dsc.nana.domain.workflow__definition.RelevantDataDefinition>
```

同一個 `relevantDataDefinitions` 底下還會有 `BasicType`（STRING 等）的流程變數。

> **注意這與資料庫端的情況不同**：資料庫裡**沒有任何一欄記錄流程與表單的綁定**，
> 得從 `formFieldAccessControl` 或主旨範本反推，兩個來源都會漏（AGENTS.md 7.1）。
> 匯出檔反而是明確的。生成時務必把 `formDefinitionId` 填對——
> 它必須等於 `form_ir.json` 的 `formId`。

## 8. ★ formFieldAccessControl —— 二次逃脫的權限

實際內容（來自 `已完成匯入_測試快速開發-欄位權限.bpmn`）：

```xml
<formFieldAccessControl>&lt;FormFieldAccessControl&gt;&lt;quickDevTestFormImport&gt;&lt;TEST_TextBox_07&gt;ENABLED&lt;/TEST_TextBox_07&gt;&lt;/quickDevTestFormImport&gt;&lt;/FormFieldAccessControl&gt;</formFieldAccessControl>
```

反逃脫後的結構：

```xml
<FormFieldAccessControl>
  <{表單ID}>
    <{欄位ID}>ENABLED</{欄位ID}>
    <{欄位ID}>INVISIBLE</{欄位ID}>
  </{表單ID}>
</FormFieldAccessControl>
```

規則：
- **欄位 ID 直接當 XML 標籤名**，所以 ID 只能是 `^[A-Za-z_][A-Za-z0-9_]*$`。
- 權限值只有 `ENABLED` / `INVISIBLE` / `FULL_CONTROL` 三種。
  **唯讀的作法是「不列出」，不是寫某個值。**
- 該關卡沒設定過欄位權限時，這一格是空的（沿用表單預設）。
- 全部清空時，把 `<formFieldAccessControl>` 移除或留空（`2_web_builder` 已實作此規則）。

`2_web_builder/index.html` 的 `CORE` 區塊已有完整的生成與回寫實作，
且有 62 項回歸測試（`node test_core.mjs`）保護。
**⑧ 產生權限字串時應與它產出完全相同的結果**，這是自檢的一個免費基準。

### 地雷：權限定義列會被多關卡共用

全庫掃描發現單一 `formFieldAccessDefinitionOID` 被 24,765 個關卡引用
（README.md 已記載）。這是**資料庫端**的問題，離線產生新檔案不會踩到；
但如果日後 ⑧ 走「線上改權限」的路，必須比照 `4_db_viewer` 先檢查引用數是否為 1。

## 9. bpmXML —— 畫布座標

逃脫過的 XML，是設計師畫面上的圖形，**不含任何流程邏輯**：

```xml
<Diagram x="0.0" y="0.0" width="1795.0" height="1050.0">
  <Node ClassName="StartEvent" Id="StartEvent_1">
    <Font name="微軟正黑體" style="0" size="15"></Font>
    <Bounds x="100.0" y="100.0" width="30.0" height="30.0"></Bounds>
    <ZIndex>3</ZIndex>
    <Background Red="220" Green="230" Blue="242"></Background>
    <Text></Text>
    <TextBrush Red="0" Green="0" Blue="0"></TextBrush>
    <ContainerNode NodeId="StartEvent_1">NoContainerNode</ContainerNode>
  </Node>
  ... DiagramLink 連線 ...
</Diagram>
```

**每個關卡 ID 在此處也會出現**（`Node Id`、`ContainerNode NodeId`、
`DiagramLink` 的 `Form Id` / `To Id`）——`bpmn_handler.write_back()` 已處理同步更新。

生成新流程時的自動排版建議（簡單夠用即可）：
- 依 `transitions` 做拓撲排序，同層放同一列。
- 起點 `x=100, y=100`；每往後一關 `x += 200`；同層分支 `y += 120`。
- `StartEvent` / `EndEvent` 尺寸 30×30，`UserTask` 等任務節點比照樣板尺寸。

座標畫得醜不影響匯入，人可以在設計師裡拖。**但節點漏掉會讓流程圖破圖。**
`bpmXML` 的節點集合必須與 `activityDefinitions` 完全一致，這是自檢必查項。

## 10. 生成流程（組裝器該做的事，依序）

```
1. 讀 process_ir.json，校驗：
   - 關卡 ID 唯一、合法
   - transitions 兩端都存在
   - 有且只有一個 StartEvent；至少一個 EndEvent；圖是連通的
   - permissions 的每個 key 都存在於 form_ir.json 的 fields
2. 依 type 挑關卡樣板，填 id / name / bpmnType
3. 產生 transitionDefinitions（Link_1…Link_n）
4. 產生 participantDefinitions，containerOID 指回關卡
5. 產生 relevantDataDefinitions，formDefinitionId = form_ir.formId
6. 產生各關卡的 formFieldAccessControl（逃脫）
7. 依拓撲排序產生 bpmXML（逃脫）
8. ★ 配發 OID（前 8 碼遞增 + 固定 24 碼後綴），全檔唯一
9. 寫檔（UTF-8）
10. 自檢：bpmn_handler.extract() 反解，與 IR 逐項比對
```

## 11. 陷阱清單

| 陷阱 | 後果 | 對策 |
|:---|:---|:---|
| 把 `workflow__definition` 的雙底線「修正」成單底線 | 解析失敗 | 標籤名雙底線、`class=`／`reference=` 單底線 |
| `.form` 那套數字 `reference` 拿來用在 `.bpmn` | 結構壞掉 | `.bpmn` 用相對路徑 `../../..` |
| OID 重複 | ⚠️ 後果未知，可能覆蓋線上定義 | 全檔唯一 + 先釐清匯入時是否重配 |
| 權限寫 `READ_ONLY` / `DISABLED` | 值不存在，權限失效 | 唯讀＝不列出 |
| 權限 key 拼錯欄位 ID | **靜默失效**，不報錯 | 校驗階段對照 `form_ir` |
| `bpmXML` 少了節點 | 流程圖破圖 | 自檢比對節點集合 |
| `formDefinitionId` 與表單 `formId` 不一致 | 關卡讀不到表單 | 校驗階段比對 |
| 直接連 190 正式區測試 | 違反 AGENTS.md 8.1 | 一律 191 測試區 |
