# 待辦的資料來源與狀態語意

> P0 驗證產出。實測時間 2026-08-24，環境為 **191 測試區**（`NaNa`）。
> 重跑方式：`python probe_todo.py`（唯讀，SOAP 只打 191 的 `fetchWorkItemCount`）。
> 取樣範圍：`WorkItem` 全表 3,396,747 筆、`LocalToDoWorkItem` 全表 1,367 筆，
> 交叉驗證取 6 名使用者（涵蓋 0 / 1 / 3 / 97 四種狀態組合）。

---

## 1. 結論（先講可以直接拿去寫程式的部分）

| 清單 | 資料來源 | 條件 |
| --- | --- | --- |
| **待簽核** | `LocalToDoWorkItem` | `userOID = 我` 且對應 `WorkItem.currentState IN (0, 1)` |
| **我申請的** | `ProcessInstance` | `requesterOID = 我`，再依 `PI.currentState` 分未結案／已結案／撤銷／中止 |
| **我經辦過的** | `WorkItem` | `performerOID = 我` 且 `currentState = 3` |

---

## 2. 最重要的一件事：`performerOID` 查不到待辦

直覺的寫法是「`WorkItem.performerOID = 我` 且未完成」，
`BPMGeneralController.js` 查簽核歷程也正是這樣接的。**但那只對已完成的關卡成立。**

實測：

| 集合 | 筆數 | 其中 `performerOID` 對得到 `Users` |
| --- | ---: | ---: |
| 未完成工作項目（`WI.currentState IN (0,1,2)` 且流程進行中） | 824 | **1** |
| 已完成工作項目（`WI.currentState = 3`） | 3,354,976 | 2,341,243 |

`performerOID` 是**「誰做的」**，關卡完成時才寫入；還沒人做的關卡該欄是 NULL。
待簽核的人存在別的地方。

> 這一條推翻了 `PLAN.md` 初版 §4.1 的待簽核定義，計畫書已同步修正。

## 3. 待辦收件匣是 `LocalToDoWorkItem`

| 欄位 | 用途 |
| --- | --- |
| `userOID` | 收到這筆待辦的人 → `Users.OID` |
| `workItemOID` | 對應的關卡 → `WorkItem.OID`，**也就是深連結要的 OID** |
| `subject` | 單據主旨，與通知信表格裡的「流程主旨」同一份 |
| `processInstanceName` | 流程名稱 |
| `createdTime` | 派送時間 |
| `workAssignmentOID` | 對應 `WorkAssignment`（本專案未用到） |

形狀：

- 全表 1,367 筆，去重後只有 972 個工作項目
  → **同一關卡可同時派給多人**，清單必須以 `LocalToDoWorkItem` 的列為單位，不能以 `WorkItem` 為單位
- `workItemOID` 100% 對得到 `WorkItem`（1367/1367）
- `userOID` 有 26 筆對不到 `Users`：25 筆是系統代理 `0000000000000000000AutoAgent0001`，
  1 筆是已刪除的測試帳號（`b77eeb14…`，流程 `testImage`）。
  兩者都不是真人，依 id／姓名查詢時自然被排除，**不需要特別處理，但也不該當成資料錯誤**

另有 `LocalNoticeWorkItem`（905,033 筆）是**通知／知會**用的，不是待簽核。本專案第一版不碰。

## 4. `WorkItem.currentState` 語意（U1、U2 已釘死）

用 SOAP 的 `fetchWorkItemCount(pUserID, 0, '0')` 當外部答案來反推，6 名使用者全數吻合：

| 使用者 | SQL 各狀態筆數 | SQL 取 (0,1) | SOAP 待辦數 | 一致 |
| --- | --- | ---: | ---: | :---: |
| S090005 | 0:158 1:36 | 194 | 194 | OK |
| S017041 | 0:116 1:1 | 117 | 117 | OK |
| YS086004 | 0:103 | 103 | 103 | OK |
| S087003 | 0:73 1:12 3:16 | 85 | 85 | OK |
| S093012 | 0:12 1:37 | 49 | 49 | OK |
| S094009 | 1:8 97:2 | 8 | 8 | OK |

得到的對照表：

| 值 | 全表筆數 | 算待辦 | 判讀 |
| ---: | ---: | :---: | --- |
| 0 | 946 | **是** | 已派送、尚未接受 |
| 1 | 354 | **是** | 已接受、執行中（對應 `acceptWorkItem` 之後的 running state） |
| 2 | 5 | 不確定 | 待辦表中僅 4 筆，且都掛在對不到 `Users` 的帳號上，取樣不到真人案例 |
| 3 | 3,354,976 | 否 | 已完成 |
| 4 | 17,812 | 否 | 流程撤銷連帶作廢（實測 100% 對應 `PI.currentState = 4`） |
| 5 | 22,652 | 否 | 已略過／收回（`dispatchType` 多為 1 或 2） |
| 97 | 2 | 否 | 見下 |

> **0 與 1 的區分是推測**（「派送 vs 已接受」），依據是 `AGENTS.md` 8.1 記載的
> 「簽核前必須先 `acceptWorkItem`，否則回 *The workitem is not running state*」。
> **但兩者都算待辦這件事是實測的**，程式只依賴後者，不依賴前者的推測。

### `currentState = 97`（U2）

全庫只有 2 筆，都是 S094009 的「刷卡人確認」關卡：

- `signoffState = 1`（全庫僅 13 筆是 1）
- `completedTime` 為 NULL，流程仍 `currentState = 1`
- **SOAP 的待辦數不計入它們**

判讀：卡住的異常關卡。清單中**排除**，但值得在畫面上另闢一個「異常」標記，
而不是靜默丟掉 —— 這是真實問題，符合 `AGENTS.md` 第 6 節的要求。

### `currentState = 2`

待辦表裡 4 筆，全部掛在對不到 `Users` 的帳號，因此沒有辦法用 SOAP 交叉驗證。
**維持未知**，程式的待辦條件只取 `(0, 1)` —— 若日後出現真人案例再回來補。
